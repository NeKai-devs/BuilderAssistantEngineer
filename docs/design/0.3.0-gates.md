# 0.3.0: gates that the agent cannot rewrite

Status: design for milestone 0.3.0. It closes the 17 findings of the adversarial review of 0.2.0. Nothing is published or promoted before the milestone closes.

## Principle

A gate may only depend on state the agent cannot write. Everything the 0.2.0 gate read while it ran (files in `.bae/`, the task file, `.claude/agents`, `.gitignore`, `package.json`) is captured before the agent starts and checked against that capture afterwards.

Threat model: the gates resist mistakes and shortcuts by an agent that edits the repository. They do not resist an agent with full access to the machine, which can replace `npm`, `bash` or the CLI itself, or write to the state directory in the user's home. The README says exactly this.

## Architecture

### State outside the repository

Everything the gate trusts lives in `~/.bae/<repo-key>/` (`BAE_HOME` overrides `~/.bae`; the tests use it). `<repo-key>` is the first 16 hex characters of the SHA-256 of the repository's real path.

```
~/.bae/<repo-key>/
  active.json                 id of the task whose capture is active
  runs/T-NNN/
    capture.json              the capture, written once when the task starts
    attempts.jsonl            one line per attempt, across invocations
    <timestamp>.md            gate report of each attempt
    lesson.md
    verify-<n>.sh             the Verification script that ran
```

`.bae/runs/` in the repository is no longer written or read. `.bae/tmp/` stays: it only holds the CLI's own scratch files (interactive prompt, codex output, last unparsed answer), which no gate reads.

### The capture

`next` takes the capture when a task goes from `pending` to `in_progress`, after its own writes (status, `## Log` heading, `.gitignore` entry) and before it launches the agent:

| Field | Content |
| --- | --- |
| `base` | `HEAD` at start, or the empty tree when the repository has no commits |
| `config` | the effective config, including commands proposed from the manifests |
| `task` | the task file text |
| `prompts` | `review`, `retry`, `lesson` and `fix-format`, already resolved from `.bae/prompts/` or the built-in ones |
| `reviewer` | the reviewer definition from `.claude/agents` or `.opencode/agent` |
| `agentsMd` | `AGENTS.md`, which the reviewer and the lesson prompt receive |
| `ignore` | the text of every `.gitignore`, `.git/info/exclude` and the global excludes file |
| `snapshot` | hashes of the files that were already uncommitted |
| `protected` | the content of every protected file (see the contract) |
| `baseline` | per suite command: exit code, output tail and parsed counts |

The gate reads only the capture. The only trusted writes after the capture are the CLI's own: task status, and a lesson added to `AGENTS.md`, which updates `agentsMd` and the snapshot in the capture.

The capture has two parts:

- Fixed: `base`, `snapshot`, `ignore` and `baseline`. They are taken once, the first time the task starts, and kept until the task is done. A blocked task that is set back to `pending` keeps them.
- Contract: `config`, `task`, `prompts`, `reviewer`, `agentsMd` and `protected`. They are refreshed from disk at the start of every `next`, before the agent is launched. Between runs only a human edits the repository. During a run, the contract is enforced after the agent exits.

`active.json` marks an agent run in flight. It is set just before the agent is launched and cleared after the gate. When the agent fails, the CLI enforces the contract before exiting. When the process is killed, the next `next` finds `active.json` and enforces that capture's contract before it reads `.bae/config.json` or the task files.

### The contract

These files are protected. Changing them during a task is a `contract` blocker. The CLI restores them from the capture and fails the attempt.

| Protected | Compared |
| --- | --- |
| the task file | everything except the `## Log` section and `status` |
| the other task files in `docs/plan/tasks/` | whole file |
| `.bae/**` except `.bae/tmp/` and `.bae/runs/` | whole file; new files are deleted |
| `.claude/agents/**`, `.opencode/agent/**`, `.claude/settings.json`, `opencode.json(c)` | whole file; new files are deleted |
| every `.gitignore` that existed | whole file |
| `scripts`, `jest`, `mocha` and `ava` in every tracked `package.json` | existing keys; new scripts are allowed |
| files the suite commands run (a script path in the command or in the `package.json` script it calls, or the `Makefile` for `make`), and files Verification runs unless the task's Scope lists them | whole file |
| runner config that existed: `vitest.config.*`, `vitest.workspace.*`, `jest.config.*`, `vite.config.*` with a `test` block, `playwright.config.*`, `cypress.config.*`, `karma.conf.*`, `.mocharc.*`, `pytest.ini`, `tox.ini`, `phpunit.xml(.dist)`, `.rspec`, `[tool.pytest.ini_options]` in `pyproject.toml`, `[tool:pytest]` in `setup.cfg` | whole file, or the section |

Creating a `.gitignore`, a `package.json` or a runner config that did not exist is allowed, because greenfield setup tasks need it; the test counts and the static test checks still apply. Changing a `.gitignore`, a script or a runner config that did exist is allowed only when the task's Scope lists that file and the user accepts the finding with `--accept-finding <id>`.

Read-only runs of the `claude` backend (review, lessons, plan) pass `--setting-sources user`, so hooks and permissions in the repository's `.claude/` do not apply to them.

### Changes seen by the gate

The changes are `git diff <base>` plus untracked files, filtered by the ignore rules in the capture, not by the current `.gitignore`. A `.gitignore` the agent edits or creates cannot hide a file. Files that were already uncommitted before the task and are unchanged since are left out, as in 0.2.0, but their hashes now live in the capture.

### Gate stages

```
contract → regression and test counts → Verification → mechanical review → reviewer
```

1. `contract`: compare with the capture, restore, and fail if anything was changed.
2. `regression`: run lint, typecheck, build and test from `commands`, compare each one with its baseline and check the test counts.
3. `verification`: run the task's block as one bash script. Lines that repeat a suite command reuse that command's result instead of running it again.
4. `handoff`: a warning only.
5. `mechanical`: secrets, test integrity from the diff, `tests: required`, scope.
6. `reviewer`: the LLM review of a budgeted diff.

A stage that cannot run fails closed. `skipped` never leads to `done`.

## Decisions per area

### 1. Trust boundary (findings 1, 2, the reviewer definition in 7, `.gitignore` in 8)

As above. The base commit is verified with `git rev-parse --verify <base>^{commit}`. If it no longer resolves (history rewritten and pruned), the review fails instead of falling back to `HEAD`.

### 2. Fail closed (4, 5, 6, fail-open in 7, 10, 11)

- These cases leave the task `in_progress` with a reason, or stop `next` before it launches the agent: no git repository or no `git`, no baseline, a baseline command that timed out or could not start (`exit -1`), the user declining the baseline, a reviewer answer that is not valid JSON after the format retry, and a reviewer backend error. When the cause is known before the agent starts (no git, no baseline, Verification refused), `next` stops there and launches nothing.
- `--allow-skip` lets the task continue without the stage that could not run. Each use is written to the run log and to the attempt record (`skips`).
- The baseline is always taken before the agent starts. A task that is `in_progress` without a capture (started by 0.2.0) cannot be completed. The fix is to reset it to `pending`, or to use `--allow-skip`, which takes a late capture and records that.
- Results are compared by counts parsed from the runner's output: executed, passed, failed and skipped tests, or errors for linters and type checkers. The exit code is only a fallback. Parsers cover vitest, jest, mocha, node:test, bun, deno, pytest, unittest, go test, cargo test, rspec, minitest, phpunit, dotnet test, maven surefire, tsc, eslint, biome, ruff and mypy.
- Regression rules per command:
  - Green before: it must stay green.
  - Red before, counts on both sides: it is a regression when failures go up or passes go down.
  - Red before, no counts: it cannot be compared, so the task cannot be done while the command stays red. `next` says so before it launches the agent.
  - `exit -1` after the task: always a regression.
- `tests: fix` is a new test policy that the analyst sets on tasks whose goal is to repair tests. For those tasks every suite test command must end green, and a red suite command in Verification is never excused. For other tasks, a Verification line that repeats a suite command that was already red is excused only when the regression stage found no regression for that command.
- `typecheck` and `build` join `lint` and `test` in the suite when they are in `commands`. The baseline is stored per command string, not per key (17).
- Retries are counted from `attempts.jsonl` in the state directory, across invocations. The budget is 3 attempts since the last time the task was `blocked`. Every way out of an attempt records it: pass, gate failure, agent error, agent timeout, reviewer error, refusal, decline.
- The headless agent gets a timeout, `agent.timeoutMinutes` in the config, 45 by default. A timeout is a recorded attempt with stage `agent`.
- `refused` (Verification not allowed, trivial or missing, or no bash) moves the task to `blocked` with the reason. The reason is shown by `next` and `status`.
- `pickNext` order: `in_progress` with attempts left, then ready `pending`, then `in_progress` with the budget used up.

### 3. Test integrity (3, 14)

Both kinds of check are blockers:

- From the counts: fewer tests executed, or more skipped, than in the baseline.
- From the diff: deleted test files; new `.skip`, `.only`, `xit`, `xdescribe`, `xtest`, `test.fixme`, `@pytest.mark.skip`, `pytest.skip(`, `@unittest.skip`, `t.Skip(`, `#[ignore]`, `@Disabled`, `@Ignore`; a new runner config with exclusion keys (`exclude`, `testPathIgnorePatterns`, `testIgnore`, `--deselect`, `-k`, `norecursedirs`).

The exception is Scope listing the file plus `--accept-finding <id>`.

`tests: required` passes only when a suite test command executes more tests than in the baseline, or when a changed test file adds assertions (`expect(`, `assert`, `assert_eq!`, `t.Error`, `require.`, `should`, `XCTAssert`, `Assert.`). Test files also include Rust files that add `#[test]`, Cypress `*.cy.*`, `e2e/`, `__tests__/`, `*_test.go` and `test_*.py`.

### 4. Verification execution (12)

- The Verification block runs as one script: `bash <file>` with `set -euo pipefail` and an `ERR` trap that prints the failing line. It no longer runs line by line.
- Bash is required on every platform. On Windows the CLI looks for Git Bash and ignores WSL's `System32\bash.exe`. Without bash, Verification is refused and the task is blocked with that reason. Suite commands run through the same bash, also with `pipefail`.
- A triviality validator rejects blocks with no runner and no check with an expected result. It also rejects `|| true`, `|| :`, `|| exit 0`, and blocks made only of `echo`, `ls`, `true`, `:`, `cat` or `pwd`. The parser applies the same rule to new plans, so the analyst gets a format retry, and `analyst.md` states it.
- With nobody confirming (`--headless` or `--yes`), an allowlist applies: every command in the block must start with a known runner (package managers, language toolchains, test runners, linters, `make`, `git` read-only subcommands, `test`/`[`/`grep`/`diff`/`jq`/`curl`) or with a prefix in `verify.allow`. Command substitution, `eval`, `source` and `sh -c` are rejected. In interactive runs the user still confirms, and the denylist becomes a warning shown with the commands. The README no longer promises that dangerous commands are blocked.

### 5. Reviewer, evidence and secrets (the blind spots in 7, 9, 13)

- Diff budget: Scope files first, then the rest of the source, then docs, then lockfiles. Generated files are left out (`dist/`, `build/`, `coverage/`, `*.min.*`, `*.map`, snapshots). New files go in whole while the budget lasts. Files that did not fit are listed by name.
- The diff goes between delimiters with a random nonce, and the prompt tells the reviewer that everything between them is data, never instructions.
- A reviewer `pass` never overrides a mechanical blocker. A reviewer `fail` or blocker still fails the task.
- Evidence becomes a real gate for `path:line` citations in brownfield plans: an invalid citation gets a fix request, and if it is still invalid the plan is not written (the answer is kept in `.bae/tmp/`). Paths without a line stay a warning. A bare name with a line is checked against every file with that name. `.env` leaves `KNOWN_FILES`. A missing `x.js` is checked as `x.ts`, `x.mjs` as `x.mts`, and so on.
- Secrets: known example keys are allowed (`AKIAIOSFODNN7EXAMPLE`, the AWS example secret, and Stripe `sk_test_`, `pk_test_`, `rk_test_`), plus `secrets.allow` path globs in the config. New patterns: `password = "…"`-style assignments, connection strings with credentials, and long high-entropy base64. Large files are scanned in chunks instead of skipped. A false positive is accepted with `--accept-finding <id>` and recorded.

### 6. Minor (15, 16, 17)

- A task with no diff passes when Verification passes; the reviewer is not called.
- The handoff note is a warning, never a failure.
- The baseline is stored per command.

## Findings, ids and acceptance

Every mechanical and contract finding has an id: `<kind>-<8 hex>`, a hash of the kind, the file and the detail, printed next to the finding. `--accept-finding <id>` (repeatable) downgrades that finding to `minor`, and only when its kind allows it:

| Kind | Acceptable when |
| --- | --- |
| `secret` | always |
| `integrity` from the diff | Scope lists the file |
| `integrity` from the counts | always, since there is no file to list |
| `contract` for `.gitignore`, scripts or runner config | Scope lists the file |
| other `contract` (`.bae/`, task files, agents) | never |

Accepted findings are written to the run log and to the attempt record.

## Durability

Each finding becomes an end-to-end test in `test/e2e/bypass/` that tries the evasion and asserts the gate stops it, or asserts the false positive is gone. That is 17 files, all in CI on the three operating systems. After that, a fresh adversarial review runs in a new session. The milestone closes when it finds no critical or high findings.

## Assumptions and deviations from the brief

- Declining the baseline stops `next` before it launches the agent and leaves the task `pending`, instead of running the agent and failing afterwards.
- The allowlist applies whenever nobody confirms: `--headless` or `--yes`. The brief only named headless.
- Other task files, `.claude/settings.json` and `opencode.json(c)` join the contract, because they can unblock tasks or change how the reviewer runs.
- Creating a `.gitignore`, `package.json` scripts or a runner config that did not exist is allowed. Changing an existing one needs Scope plus `--accept-finding`.
- A lesson added to `AGENTS.md` is a trusted CLI write and updates the capture.
- Interactive attempts count toward the budget but never block. They only lower the task's priority in `pickNext`.
- `.claude/settings.local.json` is not protected, because interactive agents write their permissions there. `--setting-sources user` keeps it out of the reviewer run for `claude`. For the other backends it remains a documented risk.

## Phases

Each phase is one commit with its bypass tests, pushed to `feat/0.3.0`:

1. Trust boundary: state directory, capture, contract and restore, captured ignore rules. Tests 01, 02, 07-reviewer, 08.
2. Fail closed: counts, per-command baseline, typecheck/build, `tests: fix`, `--allow-skip`, budget, timeout, refused→blocked, `pickNext`. Tests 04, 05, 06, 10, 11, 17.
3. Test integrity. Tests 03, 14.
4. Verification as a bash script, triviality, allowlist. Test 12.
5. Reviewer diff, evidence gate, secrets, `--accept-finding`. Tests 07, 09, 13.
6. Minor. Tests 15, 16.
7. README threat model, then the fresh adversarial review.

## Second review

A fresh adversarial review of the first six phases found 32 findings, 6 critical and 6 high. The design changed in these ways:

- Code the checks run is code the agent wrote. The state directory is guarded around every run of it (the agent session, the baseline, the suite and Verification), and the contract is checked again after the suite and after Verification.
- Git is treated as agent-controlled input. Gate commands ignore replace refs, fsmonitor and diff prefixes, and diff with `--text`. `.gitattributes`, `.git/config` and `.git/info/attributes` are protected, new index flags are cleared, and a git error fails the review.
- The CLI owns the task status. It removes duplicate status lines and resets the status after agent errors and killed runs.
- The contract grew: toolchain settings, memory files, `tsconfig`, lint configs, `conftest.py`, runner setup files, and files that would shadow the runner. Only files a command executes are protected, not its arguments.
- Counts come from the last summary of the runner the command uses. Counts that vanish block. With a red suite, a failing test name that is new blocks. Removed tests and lost assertions block from the diff.

Each finding in scope has a bypass test, numbered 18 to 29.

## Third review

Three narrower reviews (the trust boundary, regression and test integrity, Verification and the review) found 0 critical, 15 high, 26 medium and 23 low. The changes:

- Contract:
  - Existing Makefiles are protected.
  - Scripts run through `yarn`, `pnpm`, `npx`, `exec` and `pre`/`post` hooks are followed.
  - Symlinks in watched folders count as files.
  - A failed restore is retried by the next run.
  - Acceptance is tied to the file's content.
  - The baseline run is checked against the contract.
  - More configs are protected: tables and subtables of `pyproject.toml`, `setup.cfg`, `tox.ini` and `Cargo.toml`, `turbo.json`, `nx.json`, babel, prettier and coverage configs, and memory files at any depth.
- Verification: every top-level line must end with status 0, so failures inside `&&`, `if` and `!` count. The unattended allowlist refuses releasing subcommands, process substitution and `command`.
- Changes: nested repositories are walked, binary files are decided by their content, and symlinks are shown as links.
- Tests:
  - Suppression comments, snapshot and golden changes, expected-failure markers and focused tests block.
  - `tests: required` needs a net gain in assertions.
  - Removed tests only count as kept when their name is added back in a test file.
  - A command that exits 0 but reports failures is red.
  - With a red baseline, failing files and packages count as names, and counts are compared only when they come from the same runner.
  - Go needs `-v` for counts, tsc errors are counted without a terminal, and Playwright and more summary forms are read.
  - `CI=true` is set for the checks.
- Secrets: unquoted assignments, PGP keys, `ASIA` keys, Slack webhooks and lowercase hex are found. Identifier-like values, common development passwords and deleted key files are not flagged.

Bypass tests 30 to 32 cover the high findings of this round.

## Structured results

Before the fourth review, the test verdict stops depending on text heuristics wherever the runner has machine-readable output.

| Runner | How bae reads it |
| --- | --- |
| vitest | `--reporter=default --reporter=json --outputFile.json=<file>` |
| jest (also `react-scripts test`, `craco test`) | `--json --outputFile=<file>` |
| pytest | `--junitxml=<file>` through `PYTEST_ADDOPTS`, so it also works behind `make`, `tox` or a script |
| go test | `-json`; the events are turned back into text for the log, and only tests that had a `run` event count |
| dotnet test | `--logger trx --results-directory <dir>`, every TRX file summed |
| cargo test | its standard output; captured output of failing tests is ignored |

The report goes to a new temporary directory outside the repository. The flags are added only when the command is a single runner invocation, directly or through a chain of package scripts (npm gets one `--` per hop). A compound script, `make`, or flags that would clash (`--outputFile`, `--json`, `--results-directory`, `-args`) leave the command as it is.

Rules:

- A test command's runner is recognized from the command, the package scripts it calls and the Makefile recipes it runs. When no runner is recognized, `next` stops before launching the agent; `--allow-skip` leaves the command out and records it.
- Without a report, a recognized runner is read from its last printed summary, as before.
- A test command that exits 0 without counts, or whose counts come from a different reader than its baseline (for example the report went missing and only a printed summary is left), has the verdict `unknown`. It blocks, and it is never `passed`. With `--allow-skip` it is recorded as a skip.
- A baseline test command that passes without counts is unusable, like a red one without counts.
- Lint, typecheck and build keep the exit code as their verdict; their counts only compare a red command with its red baseline.

`test/e2e/legit` runs real vitest, go, cargo, pytest and dotnet projects through `next`: a correct change must end `done` and read its counts from the report, and a change that breaks a test must be blocked. Runners that are not installed are skipped.

## False positives

A gate that blocks correct work is as serious as one that lets broken work through. Running `next` on the eval fixtures with plans written by the analyst showed two such blocks before any agent code was judged:

- The unattended allowlist refused `sh scripts/lint.sh`, which the analyst writes for scripts the task creates. `sh`, `bash`, `dash`, `zsh` and `ksh` running a script file inside the repository are now allowed like `node script.js`; `-c`, `-s`, `-i`, long options, paths outside the repository and a script downloaded in the same line stay refused.
- The contract restored `.gitignore`, `package.json` scripts and runner configs that a baseline-tooling task must change, although its Scope listed them, and the only way through was to accept each finding by an id that changes with the content. Now, for those three kinds, a change to a file the Scope lists stays, is reported as a major finding and goes to the reviewer. It is still restored and blocks when it weakens the checks: a changed script that no longer runs a tool it ran (read from the script and the scripts it calls), a removed script, or a runner config or `package.json` runner block that gains a setting that leaves tests out. The captured ignore rules still decide what the review sees, so an edited `.gitignore` hides nothing. Memory files, git attributes and toolchain settings still need Scope plus `--accept-finding`.
