◇  Summary ────────────────────────────────────────────────────────────────────╮
│                                                                              │
│  go-service is an internal Gin HTTP service. It will expose GET /health      │
│  plus GET and POST /users, with users kept in memory. Right now the repo is  │
│   a stub: `handler.Run()` does nothing (`internal/handler/handler.go:3`),    │
│  and gin is listed in `go.mod:5` but no code imports it and there is no      │
│  go.sum.                                                                     │
│  Approach: keep the existing `internal/handler` package and add              │
│  `internal/store` for users. Server startup and shutdown move into           │
│  `main.go` behind `run()`. One script, `scripts/check.sh`, runs gofmt, vet,  │
│   staticcheck and the tests, both locally and in CI.                         │
│  Plan: 3 phases, 5 tasks. Phase 1: quality gates, CI and a working /health   │
│  (T-001, T-002). Phase 2: the users API, which is the first deliverable      │
│  (T-003, T-004). Phase 3: request IDs and JSON logs (T-005).                 │
│  Risks: (1) the user fields are a guess ({id, name, email}, email must be    │
│  unique) and other teams will code against them, so confirm before T-003.    │
│  (2) Users are lost on restart and not shared between copies of the          │
│  service, so run a single instance. (3) Go 1.23 is no longer supported       │
│  upstream, and staticcheck plus module downloads need network access and a   │
│  staticcheck version that works with your Go.                                │
│  Next: answer the questions (the user fields matter most), then run /next    │
│  to start T-001.                                                             │
